# 按表单审查和整理 Issue

只有一个现有表单。AI 填表单，表单拼装 Issue。不能先自由写正文，再声称符合表单。

**表单摘要要保留。** 不得把“摘要”一概判成多余章节；按表单检查摘要的字段、内容和写法。用户已明确要求保留摘要，生成时不能丢掉。

标题只写 Linear 标题栏，项目、负责人、状态、优先级、估点写右侧 Properties；正文从摘要开始，不重复标题或基本信息。表单保留这些输入，统一生成原生字段和正文。模块只匹配团队已有标签或自定义属性；编号、原链接用于定位，类型用于匹配团队分类，不能伪造不存在的原生字段。未知值不清空已有属性。

任务和验收案例沿用 Given／When／Then 的组织方式，但界面与正文只显示“前提条件／操作／预期结果”。任务直接描述通用业务行为，不再另设业务规则；案例通过 taskRef 关联任务。删除用户流程章，目标预期章下直接写内容，不重复字段标签。案例不设执行元信息，正文不生成完成条件章。

1. 阅读 [执行流程](references/workflow.md)，读取现有表单的字段定义、生成模型和对应类型的写法要求。
2. 逐项检查表单字段、重复条目、步骤和约束；同时清查 Issue 多出来的字段与章节。有用内容归回规定字段，其余从目标正文清理掉。
3. 先填当前表单草稿，用 [生成脚本](scripts/assemble-issue.mjs) 校验；按 [HTML 交付要求](references/presentation.md) 生成一份 LV 编辑风格的独立 HTML，只列合并后的实际问题，并展示按现有字段预填的表单；生成正文作为折叠对照，不交付 MD 索引套 MD。只审查时不写回。
4. 按 [完成清单](references/checklist.md) 核对。文字直接、简短，沿用用户的说法；不加“第一版／修订版”等版本标记。

必填项、可选项和约束都从现有表单读取，后续增加约束也用同一来源。不要在本 skill 复制一套字段定义，也不要为迁就某条 Issue 擅自改表单。
