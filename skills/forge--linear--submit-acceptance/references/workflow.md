# 验收交接流程

## 1. 确定本次操作

团队流程是：完成实现或其他交付 → 按 Issue 标准自验 → 在 comment 留证据并 @ reviewer → In Review → reviewer 复核 → 通过后 Done；未通过则反馈、修复、补充新证据再提交。

- 用户要求“提交验收”“交给某人 review”“完成后按流程交接”或明确调用本技能执行该流程，授权范围内包含对应 Issue 的证据上传、评论、提及已确认的 reviewer，以及转入 In Review。已有授权持续有效，不重复要求确认。
- 仅“看看”“理解流程”“起草评论”“检查证据”不授权外部写入；准备完整草稿并说明未发布。
- 没有目标 Issue 时，先从当前任务的明确关联定位；仍不唯一则询问。历史示例中的 Issue 编号不作为当前目标。
- 本技能不自动创建 Issue、修改正文/估点/负责人、部署应用、发布 Agent 配置、合并 PR 或给其他人发送消息。

## 2. 读取 Issue 和实际 reviewer

只使用用户自装 Linear MCP，例如 linear_code_forge_official、linear_fitness_club、linear_tellyn；不得改用 Codex 内置 Linear。按目标项目选择连接，工具缺失时报告缺口，不安装或替换连接。

先发现当前工具参数，再读取 Issue 的正文、Task、AC、状态、所属团队及评论；有分页就续页。只读与本次交接有关的资料，不盘点无关项目。

reviewer 优先取用户本次或本会话已指定的人，其次取该 Issue 明确的评审指派或团队已确认的规则。评论中偶然出现的人、Issue assignee、创建者和历史示例里的成员 都不自动等于本次 reviewer。

通过当前连接核对真实成员身份与工具支持的 mention 写法，例如 save_comment 支持 @displayName。重名、身份不明确或 reviewer 缺失时先完成证据和评论草稿，再询问缺失信息；不要把字面量 @reviewer 发出去，也不要猜一个人代替。

读取团队实际状态，不只凭状态类型判断：In Progress 和 In Review 都可能属于 started。Issue 已在 In Review 则无需重复切换；已经 Done/Canceled 的事项先报告现状，不擅自重开。

## 3. 按原验收标准准备证据

Issue 正文约定预期，评论记录本次实际结果。沿用原 Task/AC 编号，不能为凑通过而改标准；原标准含糊、缺具体预期时指出缺口，不根据实际输出倒填标准答案。

每项记录以下内容：

- 输入：本次实际使用的完整问题、测试数据或可取得的固定样本。
- 预期输出：Issue 约定的具体答案、编号序列、页面结果或交付内容。
- 实际输出：真实返回值、回复原文、界面结果或文档复核结果。
- 证据：直接对应这项结果的截图、录屏、测试报告、可访问运行记录或交付文档。
- 判定：通过、未通过、未验证；失败项说明具体差异。

同时记录验证环境/入口、版本标识、验证时间。可用部署版本、commit、文档修订号或测试产物标识，按任务性质选择；未核实版本就明确未知。时间按用户时区。

证据覆盖验收项，也核对 Task 的独立验收条件；若 Task 没有 AC 编号，使用原 Task 编号说明，不漏项。文档/Research 任务用实际文档片段、研究结果及复核记录，不虚构界面或自动化测试。

业务行为要求真实端到端结果时，PR、代码改动、CI 通过、模拟回执和本地截图只能证明各自覆盖的部分。历史截图不代表本版本已复测，原型、规格讲解视频也不是产品实际验收证据。证据必须匹配评论中的环境与版本。

能够在现有授权和环境下执行的验证直接完成；缺设备、凭据、资料或业务核定答案时，写“未验证”并列出缺口，不能编造证据。所有约定验收项自验通过后，才按正常流程申请整体验收。有失败/未验证项时保留工作状态并交付缺口；用户明确要求部分评审时，评论标明范围、缺口及“部分交接”，不要宣称整条 Issue 自验通过。

## 4. 写评论并绑定证据

使用评论模板，保持简洁：完成内容、环境/版本/入口、逐项输入输出与证据、reviewer 提及。没有必要时不附长篇实现过程。

本地证据保存在实际项目根目录 docs/ 下，按 Issue 和本次验证批次归档。不要在评论里放本地绝对路径或 file:// 链接。

获授权后，通过该连接支持的文件上传工具嵌入评论。例如 prepare_file_upload：逐个准备、在有效期内 PUT 原始字节、原样传递签名请求头，再将返回的图片/文件 Markdown 放进评论。不得并行申请多个短效地址，不内联 base64。已有可访问证据可直接引用；需要上传时不能用“本地已有文件”代替。

确认上传成功后再发布一条包含完整证据和真实 mention 的交接评论。不要先发空通知再补证据。只更新自己本次明确拥有的草稿，不覆盖别人评论或无声改写历史验收结论。

## 5. 回读评论，再更新状态

发布后 list_comments 回读，核对 Issue、评论 ID、AC/Task 覆盖、输入输出、证据链接和 reviewer mention。可验证的附件应打开或下载核对，上传文件可比较大小或 SHA-256；仅返回上传成功并不足以证明评论已有证据。

工具回读能够确认评论含 mention，并不等于确认 reviewer 已收到通知；无法验证通知投递时只报告“评论已提及某人”，不声称“对方已收到”。

评论超时或返回不确定时先回读查找同一 Issue、同一版本和同一批次的内容，确认未写入后才重试，避免重复评论和重复 @。连续两次明确失败则保留本地评论和证据，报告失败环节，不盲目重复发送。

证据评论确认无误后，按授权仅把 state 改为团队的 In Review，并 get_issue 回读。状态写入结果不确定时同样先读取再重试；评论成功而状态失败时分别报告，不因补状态重发评论。

## 6. reviewer 复核及再次提交

提交人自验通过、PR 合并或无人回复都不是 reviewer 验收通过。只有实际 reviewer 明确给出通过结论，且用户授权本次闭环状态操作时，才可转 Done；转前核对评论结论对应当前版本与验收范围，转后回读。

reviewer 未通过时保留具体 AC、输入、实际结果和差异，按当前修复授权处理。重新提交用新评论记录修复版本和新证据，并再次提及 reviewer；保留旧证据和评审历史。是否转回 In Progress 依据已有团队规则和当前授权，不擅自改变其他属性。

提交到 In Review 并回读成功后即完成本次交接。除非用户明确要求持续跟进，不轮询等待 reviewer，不创建自动提醒。

## 7. 最终回复

简要返回 Issue/评论真实链接、reviewer、实际状态、证据位置及未完成项。无评论 URL 时使用 API 返回的 Issue URL 与评论 ID 定位，不拼造 comment 链接。仅草稿、上传失败、mention 不可核对、状态未改变都要准确披露。
