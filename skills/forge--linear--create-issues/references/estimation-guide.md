# Linear Issue 拆分与估点

## 点数边界

- 单条 Issue 只使用 8 或 16 点，不使用 12 点或其他档位。
- 一个 Task 使用 1、2、4 或 8 点，按实际范围设置 1～4 个 Task；Task 点数之和必须等于 Issue 点数。
- 1 点表示一个边界明确的小改动；2 点表示已有流程中的一个业务步骤；4 点表示有多个关联状态的一项完整业务能力。
- 超过 16 点的真实范围应按独立业务结果拆开；16 点是合法档位，不因点数强制拆成两条 8 点。用户只授权调整现有事项时，先缩小或明确待拆范围，不擅自创建新事项，也不把大范围直接压成 8 点。

## Task 必须交付主动业务结果

先按 `task-writing.md` 明确这项交付改哪里、具体改什么、完成后有什么业务效果，再估点。用户能做什么用于判断业务价值，不能直接把用户操作步骤当作 Task 标题。例如，新增供应商驳回入口并要求填写原因；补齐原采购单修订重提流程；在财务往来详情增加期间账款明细。

权限判断、必填校验、禁用、取消、版本变化、幂等、防重复、重试、异常提示和历史数据兼容，默认都是主流程的验收条件，不单独形成 Task，也不因出现这些词自动加点。保留与业务真实风险相关的条件，删去没有具体场景的“兜底”“健壮性”“保护状态”表述。

只有同时满足下列条件，才可以独立保留防御性质 Task：

1. 已有具体故障或明确业务风险，如重复入库会实际增加库存，且不能由现有能力直接承担。
2. 提供独立可操作、可验收的恢复或核对流程，有明确角色、入口和结果；普通校验失败不满足。
3. 说明为什么不能归入相关业务 Task 的验收条件，并标明它依赖的业务 Task。

满足例外也按实际范围给 1 或 2 点，不默认 4／8 点；超过 2 点说明它已是独立产品能力，应重新定义为业务结果并评估拆分。

## 估点依据

- 以需要新交付的业务步骤、跨页面操作和既有能力复用为依据；外部文档未齐是依赖，不把不确定性虚构成额外任务。
- 首先删除重复或泛泛的防御 Task，再估具体业务交付；不能只改点数字面值。
- 不按文件数、代码行数、测试条数或 AI 编码速度计点；不把数据层、接口、页面和测试拆开收费。
- 没有新的异常处理界面或流程时，不额外承诺异常中心、重放平台、补偿平台或历史清洗。

## 示例

| 需求 | 主动 Task | 总点数 | 随主流程验收的条件 |
|---|---|---:|---|
| 独立团队目录并复用额度详情 | 团队查询列表 4；关联详情与来源返回 4 | 8 | 分页、权限、空态与查询失败重试 |
| GitHub PR 合并门禁 | 配置并核实仓库门禁 4；新旧 PR 检查与合并约束 8；结果追踪与复查入口 4 | 16 | 当前版本匹配、幂等、超时不放行与访问隔离 |

小于 8 点的零散改动先并入业务目标一致的需求，或保留待规划；不添加无关功能、虚增估点或使用 Bonus 凑点。

## 完成前核对

确认每个 Task 的标题和首段能直接定位待交付改动，写清具体变化及业务效果；Issue 只能为 8 或 16 点且总分一致；没有把必要校验删掉，也没有把通用防御扩写成主交付。
