# 表单驱动的 Issue 创建流程

## 1. 授权与真实上下文

先确认目标连接、项目、团队和本次是只读起草还是创建/更新。只用用户自装 Linear MCP，不用 Codex 内置 Linear；已有同范围授权持续有效。读取相关 Issue 的正文和必要评论/附件，查重，核对现有能力、真实角色、页面和实际缺口。用户没有授权写入时不修改 Linear。

先读统一最佳实践和字段契约，不从其他旧模板拼装正文。读取实际数据，不编账号、URL、样本、截图或已完成结果。索引仓库先按项目要求使用 CodeGraph。项目临时及评审产物保存项目 docs/。

## 2. 表单选择与范围

当前统一开发表单提供 Feature、Bugfix：新增或改变能力用 Feature，恢复已约定行为用 Bugfix。表单类型不等于 Linear 标签；已有 Bug、Opt 等分类按实际团队标签保留和匹配。不能因为表单选 Feature 就把原生 Opt 改为 Feature。

Doc、Research 或当前字段无法表达的需求先说明具体承载缺口，完成可确定的材料后询问；不假选类型、不绕过表单另造正文。纯后台需求不虚构界面；当前表单无法承载的执行方式明确列为缺口，不假选下拉选项。

按当前字段契约填写范围、Task、规则及案例。Task 写清具体做什么及对应的输入/预期输出，依实际工作顺序组织，不另造复杂子任务模板。验收 Given 只列当前必要状态，When 给具体输入操作，Then 给可核对输出，必要时细化步骤。来源不够就留待补，不用实际输出倒填标准答案。

普通计划估点沿用已确认项目口径；worktree 事后补录按 forge--linear--backfill-issues 中实际投入每小时 1 点、逐 Issue 汇总向上取整，不受旧 8/16 档限制。点数只写原生属性，不为了凑点扩大工作。

## 模块负责人

按 [模块负责人分配](module-ownership.md) 读取项目内绑定、解析有效用户并填入表单 assignee。创建请求一起设置原生 Assignee，不因用户没有再次点名就留空。只审查或本地起草时不写入人员分配。

## 3. 固定生成

保存项目 docs/issue-form.json。可用同级表单的 show-issue-form.ts --input 预填页面编辑；旧草稿先归一化并保留原始资料，缺项必须人工补齐，不能因迁移有结果就当已可验收。

运行 scripts/assemble-issue.mjs --input PROJECT/docs/issue-form.json --output PROJECT/docs/issue.md --linear-output PROJECT/docs/issue-linear.json。它委托同一表单生成器，不另维护第二套字段或映射。

必填、关联或执行条件不满足时禁止完整生成；--draft 只用于保留待补稿，仍拒绝未知字段。按需将已有完整材料交给用户确认；不能把缺资料的草稿称为定稿或已验收。

读取 issue-linear.json：fields 是待核对的原生字段，context 是定位信息，unmapped 是需匹配真实团队配置的内容。模块/类型不直接伪装成不存在的 API 字段；未知属性不清空原值。

正文直接使用生成的 description，不手工重排、翻译另一份、添加章节或追加基本信息。需要修改先回到 JSON，再生成。语言要求在字段内表达，生成结构保持唯一。

## 4. 附件与独立验证

原有自包含逐 Task 讲解视频、静态规格及独立形式化验证等适用交付要求继续有效；先读对应产物规范。所有业务文案均从同一表单/生成块取得，不能让旧静态模板或形式化反向文本覆盖 issue.md。无法生成或验证时明确报告未完成，不拿静态 HTML 当已完成视频。

形式化语义只作独立核对，不是第二个正文源；不能凭验证通过替代实际业务验收。不得因为当前任务只是更新技能而虚构一条业务 Issue 并生成其附件。

## 5. 写入与回读

写入前执行 scripts/validate-issue-body.mjs --form PROJECT/docs/issue-form.json PROJECT/docs/issue.md，核对正文逐字等于同一生成器输出且未混入内部证明材料。仅通过旧的敏感词/证明泄漏检查不等于按表单生成。

确认真实团队、项目、状态、标签、负责人和点数，更新只传获授权变化的字段。已正确的原生属性不重复清空；context/unmapped 不直接传作 API 参数。缺写入授权时交付完整本地草稿和待补，不发送。

获授权后提交 fields.description 与生成正文相同的内容，上传适用附件并真实绑定、下载回读。回读 Issue 核对标题、属性、正文；如平台做格式标准化，逐项核对实际差异并保留记录，不把回读正文重新当另一份可自由编辑模板。

超时先回读查重后重试，部分成功逐步报告；不重复创建或覆盖他人新改动。完成工作后留证据、@ reviewer、In Review 到 Done 的流程按对应验收技能，不因创建了 Issue 就宣称功能完成。

## Linear 人物格式

人物正文使用标准 Markdown 斜体（星号包裹），由共用模型生成；HTML 预览同步斜体，不复制 HTML 标签到 description。标题和原生属性保持纯文本。试用只写回用户指定示例，不自动批量修改历史 Issue。
