# Issue 视频 HTML、静态规格与 Lean 产物规范

**最低交付规则：** 所有类型的 Issue（含 Doc、Research、新人入门、资料阅读与走查）至少交付一份逐 Task 的自包含 HTML 讲解视频；双语按语言分别生成。非开发任务讲清要学什么、做什么、交什么及谁来复核，不虚构产品改动或自动化验收。获授权写入 Linear 后须绑定真实视频附件、下载并核对文件大小与 SHA-256；未完成时不得报告整条 Issue 已完整交付。


## 交付边界

交付优先级固定为：**视频 HTML → 静态规格 HTML → 本地 Markdown / Lean 内容源与验证材料**。默认生成对应语言的自包含 `issue-video-zh.html` / `issue-video-en.html`，首个预览链接、优先验收项及获授权的上传均为视频 HTML；`issue.html` 是详细规格参考。不得因任务类型或粒度自行跳过视频。生成依赖按内容源、脚本、旁白和画面先后处理，不能将依赖顺序误当成交付优先级。

获授权写入 Linear 时先上传视频 HTML，再上传静态 `issue.html`；`issue.md` 与 `formalization.lean` 保留本地，仅在用户要求时上传。用户说“上传 HTML 就行”时，不追加 MP4、PDF、ZIP 或其他归档。仅本地、先审阅、暂不上传的要求优先，生成文件不自动授权写入 Linear。既有未修改附件保留，不为统一格式重传。

PDF 生成、打印预览、纸张分页调优与逐页 PDF 验收均为可选项，只有用户明确要求 PDF 或打印时才执行；HTML 上传或屏幕渲染验收不构成此授权。默认 HTML 检查不得调用 `Page.printToPDF`，不得因打印排版问题延误 HTML 交付。

## 产物时机

只有 Issue 的标题、范围、Task 和验收用例获得用户确认后，才生成文件。头脑风暴中的候选稿不落为最终产物。

## 目录与文件

每条 Issue 使用独立目录：

```text
docs/backlog/<roadmap>/<NN>-<issue-slug>/
├── issue-video-zh.html  # 默认首要交付；zh-CN / zh-en
├── issue-video-en.html  # zh-en 模式另交一份英文视频
├── video-zh/           # 可维护视频源码与嵌入媒体；本地保留
├── video-en/           # zh-en 模式
├── issue.md
├── issue.html          # 静态详细规格参考
└── formalization.lean
```

- `NN` 是路线内两位顺序号。
- `issue-slug` 使用简洁 kebab-case 产品名称，不使用尚未创建的 Linear ID。
- 创建 Linear 后可以在正文 Reference 中补 ID，不因 ID 改名目录。

## 视频 HTML（最高优先级）

默认按 [HTML 故事视频](html-video.md) 生成、配音、逐 Task 验证并打包每种语言的自包含 HTML。每条视频覆盖全部 Task 及实际页面/流程画面，包含合成女声、同步字幕和温和配乐；不把普通长文 HTML 或自动翻页幻灯片称为视频。先在本地给用户视频入口，再提供静态详细规格链接。TTS、画面、播放或自包含检查失败时，报告尚未完成的环节并保留可重试输入；不能静默降级成无声或静态 HTML 后宣称已完成。

## Markdown 版本

- Markdown 是文本内容源，Lean `canonicalPrd` 是产品语义源；Markdown 遵循 `issue-template.md`。
- Markdown 正文不得重复 Linear 已有的属性字段，不生成“字段 / 内容”元数据表。
- 折叠摘要与 Reference 使用 Linear 原生 `>>> 标题 … >>>` 语法，不使用 HTML `<details>`。
- `zh-CN` 只包含一份完整中文规格，不添加英文镜像或语言分隔线。
- `zh-en` 将中文放在前、英文放在后，中间只有一条 `---`。
- 每份语言规格都包含完整 Task 与验收标准；`zh-en` 复用相同 Task ID 与 AC ID。
- 每份语言规格都以默认折叠的摘要开头，摘要覆盖角色、交付、规则、非目标、点数。
- 表格、Task ID、AC ID 和路由必须完整保留。
- 不添加仅为 HTML 展示服务的占位文本。
- 不写入“用于评审”“已确认”“不代表最终稿”等产物生成过程说明。
- Markdown 与 Linear 正文只保留业务规格，执行 `formal-prd-lean.md` 的“正文与证明分离”规则；不包含内部形式化区块、定理标识或反向生成 PRD。

## Lean 版本

- 使用 `formal-prd-lean.md` 定义的七类有限符号，不在 Issue 语义核心中使用自由字符串或私有构造子。
- 声明唯一 `canonicalPrd`，提供 `WellFormed` 证明；存在多个来源表述时提供归一相等证明。
- 每个 Task 与 AC 都能追踪到规范值中的 `Guard` 或 `Outcome`。
- 使用当前项目锁定的 Lean 工具链编译，不得包含 `sorry`、`admit` 或未解目标。
- 从 `canonicalPrd` 反向生成的标准 PRD 是 Markdown 与 HTML 的语义输入；不得从原始对话文本生成另一份独立规格。

## HTML 版本

HTML 必须与 Markdown 内容等价，但可以重新组织视觉层级。可复用的模板、规格格式和生成命令见 [issue.html 前端模板与生成器](issue-html-template.md)；手写或改造 HTML 时仍须满足以下规则：

- 自包含 HTML 和 CSS，不依赖 CDN、远程字体或 JavaScript 框架。
- 标题、摘要、Task、流程图、原型和验收标准必须在构建阶段写入静态 DOM；完整 PRD 不得依赖客户端脚本执行后才出现。
- JavaScript 只能增强可选交互；禁用 JavaScript 后仍必须可以阅读全部产品规格。
- 生成和验证时必须遵循 [HTML 静态渲染与故障防护](html-rendering-safety.md)。
- 首屏直接展示 Issue 标题、Product、Domain、点数、优先级和依赖。
- 元数据之后提供默认折叠的中文摘要；`zh-en` 的英文规格开头提供对应的英文摘要。
- 提供桌面端固定目录，窄屏下变为顶部横向目录。
- Task 使用可扫描的阶段块，稳定显示 Task ID 和点数。
- 每份语言规格分为验收标准和测试用例两个章节；前者显示 checkbox、Task ID、AC ID、场景名称与 Given / When / Then，后者显示独立 TC ID、对应 AC 编号与名称、具体 Given / When / Then。Summary 必须与测试注释的 `@summary` 和 Markdown AC 标题一致，不显示测试实现类型。
- 用户可操作的 Issue 必须包含原型区，至少展示入口状态、主要操作页面和关键 Dialog 或菜单。
- 复杂流程 Issue 必须以同一份结构化 Flow Schema 生成 Markdown Mermaid 与 HTML 自包含 SVG，完整呈现角色、判断、异常路径和最终结果。
- HTML 流程图必须由 Mermaid、Graphviz 或等价自动布局引擎生成；不得通过 CSS 定位、伪元素连线、字符箭头或固定像素坐标手工绘制。
- 原型中的页面、路由、控件文案和状态必须来自 Task 和验收说明，不得添加尚未批准的产品能力。
- 原型可以使用自包含 HTML/CSS 绘制；它是视觉说明，Markdown 与 Task 和验收说明仍是产品语义来源。
- 不涉及 UI 的 Issue 不虚构界面，改为展示业务流程、状态流转或系统边界图。
- HTML 严格遵循所选语言模式；`zh-CN` 只有中文，`zh-en` 的中文在前、英文在后，且两部分均为包含 Task 和验收标准的完整独立规格。
- 采用编辑式长文档版式（见 [issue.html 前端模板与生成器](issue-html-template.md)）：文档外壳使用 Lieflat Mono 色板（纸色、炭黑正文、灰阶），细线与留白分层，不使用渐变、装饰性光斑、营销 Hero 或重复的圆角卡片；原型画布内是 shadcn/ui 风格的产品 UI 层，使用 `.canvas` 作用域的语义 token，错误与 destructive 状态可用克制的语义色。
- 正文与原型圆角不超过 8px，不嵌套卡片；唯一例外是 Task 估点图沿用 Lieflat Mono 图表卡（24px、无边框）。
- 提供清晰的 focus 样式、语义化标题层级和足够颜色对比度。
- 模板可保留既有 `@media print` 样式；默认无需新增、调优或验证打印样式。

### 原型按组件拆分

- 先依据 Task 和验收说明列出本次涉及的页面和独立交互组件，再分别绘制。主页面、Modal / Dialog（弹窗）、Drawer（抽屉）、Popover / Menu（浮层菜单）等应拥有独立的具名展示区，不能只交付一张混合所有界面的草图。
- 页面草图展示正常页面及触发入口。弹窗单独展示打开状态，保留遮罩、弹窗边界、标题、关闭及底部操作的位置；不得将弹窗内容画成主页面里常驻的内联表单或面板。抽屉和浮层同样保留各自的空间关系。
- 每个独立展示区标明组件名称、触发入口和当前状态，并能从文档目录或原型索引直接定位。关键差异状态（例如内置选择、自定义表单、错误反馈）分别可见或可切换，不要求先走完整流程才能找到组件。
- 按交互边界拆分，不机械地将每个按钮、输入框都拆成一张图；共用组件可集中展示，再标注使用位置。不增加 Task 和验收说明之外的组件或状态。
- 独立组件画面是必需的，串联点击演示是补充；静态画面须在禁用 JavaScript 时仍可查看。Modal 的遮罩只限于它自己的示意画布，不得覆盖需求正文或文档目录。
- 例如渠道功能分别展示：渠道列表页面、添加渠道弹窗的内置目录状态、该弹窗的自定义表单状态。它们属于一个用户流程，但不是一个常驻在列表中的大面板。

## 操作位置与现状材料

涉及 UI 时按 [操作位置与现状材料](page-location-evidence.md) 在 Markdown、Linear 与 HTML 的 Task 和操作说明中写清必要入口、页面、板块与结果，不生成独立页面定位章节或表格。现状截图与目标原型分区，已有截图内嵌到自包含 HTML，Linear 正文引用已上传可访问资源；截图作为默认 HTML 附件之外的证据例外。没有截图时标出真实缺口，不以原型替代。

## 内容一致性

生成后逐项比较：

| 检查对象 | 一致性要求 |
|---|---|
| 标题 | 与所选语言模式一致；`zh-en` 的中英文标题字符均正确 |
| 元数据 | Product、Domain、Type、Estimate、Priority 和依赖一致 |
| Task | 数量、顺序、名称和点数一致 |
| 摘要 | 每份摘要可追溯到 Task、规则、非目标、点数；`zh-en` 语义一致 |
| 原型图 | 每个关键画面能追溯到已批准的Task 与验收说明，不增加新范围 |
| 非目标 | 不得在 HTML 中省略或增加范围 |
| 验收标准 | 每份语言规格的 AC 完整；`zh-en` 的数量、ID、Task 归属、Summary 和 GWT 内容及 TC→AC 引用在两种语言中一致；HTML 卡片 Summary 与 Markdown 标题一致 |
| Lean 语义 | 在独立证明或本地验证记录中核对角色、动作、条件、结果与业务正文一致；Markdown 和 HTML 不展示证明信息 |

正文和原型只表达程序员、设计师与测试人员完成工作所需的产品事实，不保留头脑风暴、确认过程、执行建议或与用户对话中的中间措辞。

HTML 不得成为第二份独立规格。语义变化先修改 `canonicalPrd`，再重新生成 Markdown 与 HTML；纯文案变化先修改 Markdown，再同步 HTML。

## 验证

- 检查 HTML 可以直接在浏览器打开。
- 使用项目 Lean 工具链编译 `formalization.lean`，并检查不存在 `sorry`、`admit` 或未解目标。
- 对每个来源表述执行归一化，确认结果等于 `canonicalPrd`；反向文本再次归一化后仍等于规范值。
- 使用 HTML Parser 或浏览器 DOM 确认核心正文、Task、AC、流程图与原型是真实 DOM，不是仅存在于 `<script>` 中的序列化字符串。
- 禁用 JavaScript 后再次确认完整 PRD 仍然可读；不存在由空容器和运行时 `innerHTML` 注入组成的唯一渲染路径。
- 若存在脚本，执行脚本语法检查并确认浏览器 Console 无 error；不得仅以文件大小或全文字符串搜索作为渲染成功证据。
- 检查 1440px、1024px 和 390px 宽度下没有文字重叠或横向页面溢出。
- 检查原型在桌面和窄屏下保持可读，控件文案不溢出或重叠。
- 逐个打开或定位独立组件画面，确认页面入口、弹窗遮罩与边界、组件状态符合Task 与验收说明；不能仅凭一张整页截图判定原型完整。
- 检查复杂业务流程的 Schema 验证通过，Mermaid 与 SVG 的节点和边数量一致，并且图表只在自身容器内滚动。
- 仅当用户明确要求打印时检查打印预览与分页；明确要求 PDF 时才生成 PDF 并逐页检查。
- 写入前运行 `node scripts/validate-issue-body.mjs <issue.md>`；使用 HTML DOM 检查目录及正文没有内部证明区块。
- 使用模板生成时运行 `node scripts/check-issue-html.mjs <issue.html> <issue.md>` 做正则标记 lint 与 Markdown 一致性比对；它不是 DOM 验证。上方的真实 DOM、禁用 JavaScript、宽度检查仍须在浏览器中完成；打印检查按上述可选条件启用（可用 `scripts/browser/check-issue-dom.mjs`）。
- 最终回复首先提供视频 HTML 链接及实际上传结果，再提供静态规格参考；明确区分视频、静态规格、仅本地生成和已上传。其他材料按用户要求提供，无需展开定理说明。

## Linear 附件交付

- 默认先上传各语言的视频 HTML，再上传静态 `issue.html`；真实现状截图按证据规范补充上传并在正文引用；Markdown 和 Lean 是本地材料，用户要求对应格式时才作为附件交付。不得以“三版本规范”为由覆盖用户的 HTML-only 要求。
- Linear Issue 创建或更新并首次回读成功后，上传所选 HTML 真实文件附件。
- 附件上传必须使用原始文件字节，不得把本地路径或 `file://` 地址作为链接附件。
- 每个文件完成上传和绑定后立即回读确认，再处理下一个文件。
- Issue 更新时，只重传内容变化的附件；新附件上传并回读验证成功后再删除旧的同名附件。未修改的 Lean 附件保持原样，保证本次交付的每个同名文件只保留一个当前版本；未选择交付的历史附件不主动删除或重传。
- 任一附件上传或回读失败时，明确报告该 Issue 对应附件尚未完成交付。
- 视频 HTML 是默认首要附件（见 [html-video.md](html-video.md)）；完成视频验证并获授权后优先上传。仅本地或暂不上传时只返回本地链接，不创建 Issue 或上传附件。

验收内容分为“验收标准”和“测试用例”两个部分，两部分均使用 Given / When / Then。验收标准按独立业务能力收敛，写必要业务前提、触发行为及业务结果；测试用例写确切初始数据、可照做的操作和可核对的具体结果，并明确标注对应验收标准的编号与名称。一个验收标准可对应多个用例，不为每个控件、校验、取消动作或通用错误分别增加验收标准。
