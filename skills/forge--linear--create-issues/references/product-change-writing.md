# 背景介绍与目标预期

起草或重写 Issue 时，使用“背景介绍”和“目标预期”两节。不单列“背景”“现状与截图 / Current State & Screenshots”；相关截图和图注随背景介绍中的系统现状一起呈现。

## 背景介绍

按以下思路组织内容，短需求可以写成连贯段落，不强制三个子标题：

1. 用户需求：具体角色在什么业务场景下，想完成什么事情。
2. 遇到的痛点：当前哪一步受阻、不能完成什么；只写已知影响，不编造损失、人工流程或效率数字。
3. 系统现状：现在已有何种能力、缺少哪种操作，与前面的需求和痛点对应。已核实的业务事实和未验证的推断要分清。

背景介绍解释为什么需要做，不写代码、框架、PR、测试数量或部署进度。必要的实现与核查信息仅保留在本地核查记录。截图用于说明现状，不能用目标原型冒充真实页面；取不到时如实在本地核查记录中说明缺口，不再加一个截图章节。

## 目标预期

说明完成这条 Issue 后，用户能通过什么操作得到什么可观察结果，逐项对应 Task 与验收。不要重复背景、罗列技术阶段，或写“提升体验”“形成闭环”等空泛收益。不要增加点数、准确率、日期或范围承诺。

## 示例

背景介绍：“汉高员工回听有权访问的会议录音时，需要修正逐字稿里的错词，并保留识别结果作为对照。现在逐段文字只能查看，发现错误后无法保存修正，整理纪要时也不能采用人工校订的全文。系统已有录音播放、全文转写和会议纪要页签，缺少逐段文字编辑及原始识别对照。”

目标预期：“有校订权限的员工可以保存逐段校订文字，刷新后仍可查看；可以对照原始识别；主动重新整理纪要时使用最新保存的全文。”

## 视频与内容一致性

视频的背景介绍同样按用户需求、痛点、系统现状说明，不能只截取需求首句而遗漏痛点和现状。目标预期与正文一致，操作细节在 Task 章节讲解。完整规格保留必要规则及验收，不逐条朗读全部技术约束。
