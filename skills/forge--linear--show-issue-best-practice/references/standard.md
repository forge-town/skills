# 开发 Issue 写作标准

以当前表单契约和用户最新确认的结构为准；报告、表单和生成正文一致。

## 先选类型

Feature 用于新增或改变能力；Bugfix 用于恢复已有约定行为。未知预期或根因不能编造，案例定义和实际执行分开。

字段、必填、枚举和顺序以 [当前契约](issue-contract.json) 为准，拼装使用 [共用模型](../../forge--linear--show-issue-form/assets/issue-model.mjs)。不手写另一套正文，不以本说明复制字段定义。

## 结构

- 标题只写标题栏，项目、负责人、状态、优先级、估点只写原生属性。未知值不清空已有属性。
- 摘要保留做什么、从哪开始、怎样算完成三项。
- 背景说明用户需要、痛点和已核实的系统现状，事实与推断分开。
- 目标预期直接写内容，不在章名下重复“目标预期：”。
- 功能概览概括输入、处理和结果；不复制详细案例。
- 只保留任务，不另设业务规则和用户流程章。
- 保留非目标；不生成参考资料或完成条件章。
- Bugfix 按其分支保留现象、复现、实际与预期、依据和排查信息，不强加 Feature 的用户故事。

## 人物统一斜体

正文中的人物角色、姓名和简称统一使用斜体。人物来自纯文本表单，不为格式创造身份；用户故事角色自动纳入，其他真实称呼填“人物称呼与姓名”。该字段不生成独立章节或原生属性。

- Markdown／Linear 使用标准 `*人物*`，不输出 `<u>`、`<ins>` 或 `<em>` 等 HTML 标签。
- HTML 预览使用原生斜体元素，人物样式与 Markdown 一致。标题栏和原生 Properties 保持纯文本。
- 保留姓名、链接地址、图片地址、代码和带引号的字面测试输入；不为了格式修改业务数据。
- 写入后回读确认人物被转换为斜体，标签没有作为普通字符出现在正文。试用先改一条，不自动批量改历史 Issue。

[Linear 编辑器说明](https://linear.app/docs/editor) 支持标准 Markdown 斜体。

## 任务写法

任务使用稳定的 T- 编号，直接采用原业务规则的写法：

- 前提条件：这一类场景的必要状态。
- 操作：用户进行什么操作，接收什么类型的信息。
- 预期结果：系统的通用处理和可观察结果，包含必要成功、缺失和冲突分支。

不再同时维护动作段、输入／预期输出条件表和另一套业务规则。具体色号、文本、图片或固定数据放到关联案例。后台入口、关键控件和必要业务约束不能因合并而丢失。

## 验收案例

每例通过 taskRef 关联有效任务，先正面再反面。每个任务至少一个正面案例，整体覆盖必要异常和边界。

界面和正文同样只显示“前提条件／操作／预期结果”；Given／When／Then 只作为内部结构，字段键仍是 given／when／then。不显示英文框架名或“按顺序执行与逐步检查”等额外标题。

操作只写一套，按序列出具体控件、完整字面输入和检查点。不先写一段操作，再重复生成一张步骤表。旧结构化 steps 仅在内部数据保留，不再单独展示或作为必填校验。

案例只列名称、对应任务、前提条件、操作和预期结果，不添加执行方式、完整执行入口、账号与组织、清理恢复或未解决条件等独立字段。必要身份与固定数据直接写在前提条件中，具体操作写在操作中；不生成未填写和缺环境说明。Bugfix 的实际状态、结果和证据如实记录。

## 写法与兼容

不增加说明性注脚、生成过程说明、重复提醒或版本尾巴。人物、原文和固定输入保持原意；HTML 样式不能变成实际输入值。

旧任务动作、条件、业务规则及用户流程保留在 legacySource 中供迁移核对。旧 BR 到新 T 的关联必须明确；不能静默改绑案例。导入不得丢失业务材料，案例定义不能冒充实测通过。

Review 采用 [简明检查与已填表单](../../forge--linear--review-issue/references/presentation.md)。只审查不写回，写回需对应授权。
