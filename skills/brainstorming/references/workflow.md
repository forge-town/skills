# Brainstorming 工作流详解

## 反模式："这太简单了，不需要设计"

每个项目都必须经过此流程。一个 todo 列表、一个单函数工具、一个配置变更——全部都要。"简单"项目恰恰是未经检验的假设导致最多返工的地方。设计可以很简短（对于真正简单的项目只需几句话），但你**必须**呈现设计并获得批准。

想着"这次跳过设计吧"？停下来。这是合理化。

## 流程概览

```
探索项目上下文
    ↓
评估范围 ──── 太大？→ 拆分为子项目，对第一个子项目进入正常流程
    ↓ （范围合适）
提问澄清（每次只问一个问题）
    ↓
提出 2-3 种方案（含推荐与理由）
    ↓
分段呈现设计 ←──── 用户不满意，修改
    ↓ （用户批准）
编写设计文档 + git commit
    ↓
规格自审（内联修复）
    ↓
用户审阅文档 ←──── 用户请求变更
    ↓ （批准）
调用 writing-plans 技能
```

**终止状态是调用 writing-plans。** 不得调用任何其他实现技能。brainstorming 之后的唯一下一步是 writing-plans。

## 九阶段任务清单

执行 brainstorming 时，必须为以下每一项创建任务，并按顺序完成：

1. **探索项目上下文** — 查看文件、文档、最近的提交记录
2. **评估范围** — 是否需要拆分为多个子项目
3. **提问澄清** — 逐一提问，理解目的/约束/成功标准
4. **提出 2-3 种方案** — 包含权衡分析和你的推荐
5. **呈现设计** — 按复杂度分段展示，每段结束后获得用户确认
6. **编写设计文档** — 保存到 `docs/specs/YYYY-MM-DD-<topic>-design.md` 并提交 git
7. **规格自审** — 快速检查占位符、矛盾、歧义、范围问题
8. **用户审阅文档** — 请用户审阅规格文件后再继续
9. **过渡到实现** — 调用 writing-plans 技能创建实现计划

## 阶段详解

### 1. 理解想法

- 先查看当前项目状态（文件、文档、最近提交）
- **在深入提问之前先评估范围**：如果请求描述了多个独立子系统（例如"构建一个包含聊天、文件存储、计费和分析的平台"），**立即标记**。不要在一个需要分解的项目上花时间细化细节
- 如果项目太大，帮助用户分解为子项目：
  - 独立的部分是什么？
  - 它们如何关联？
  - 应该按什么顺序构建？
  - 然后对第一个子项目走正常的设计流程
  - 每个子项目走独立的 spec → plan → implementation 循环
- 对范围合适的项目，逐一提问来精炼想法
- 尽量使用选择题，开放式问题也可以
- **每条消息只问一个问题** — 如果一个话题需要更多探索，拆分为多个问题
- 聚焦理解：目的、约束、成功标准

### 2. 探索方案

- 提出 2-3 种不同方案及其权衡
- 以对话方式展示选项，附上你的推荐和理由
- **先展示推荐方案并解释原因**

### 3. 呈现设计

- 一旦你相信已理解要构建的内容，呈现设计
- 根据复杂度调整每段的篇幅：直观的部分几句话即可，有深度的部分可以 200-300 字
- **每段结束后询问是否正确**
- 必须覆盖：架构、组件、数据流、错误处理、测试策略
- 随时准备回头澄清

### 4. 面向隔离和清晰的设计

- 将系统拆分为更小的单元，每个单元有一个明确的职责，通过定义良好的接口通信，可以独立理解和测试
- 对每个单元，你应该能回答：它做什么、如何使用它、它依赖什么
- 别人能不读内部实现就理解一个单元吗？你能不破坏消费者就改变内部实现吗？如果不能，边界需要调整
- 更小、边界清晰的单元也更容易被 agent 处理——你对能一次放进上下文的代码推理效果更好，文件越聚焦编辑越可靠。文件变大是它做了太多事的信号

### 5. 在现有代码库中工作

- 在提出变更前先探索当前结构，遵循现有模式
- 对影响当前工作的现有问题（如文件过大、边界不清、职责纠缠），在设计中包含针对性改进——就像一个好开发者在工作中顺手改进接触到的代码
- 不要提出无关的重构。聚焦于服务当前目标

### 6. 文档

- 将验证过的设计（规格）写入 `docs/specs/YYYY-MM-DD-<topic>-design.md`
  - （用户对规格文档位置的偏好覆盖此默认路径）
- 提交设计文档到 git

### 7. 规格自审

编写规格文档后，用全新的眼光审视：

1. **占位符扫描：** 有 "TBD"、"TODO"、不完整的章节或模糊的需求吗？修复它们
2. **内部一致性：** 各章节是否互相矛盾？架构是否与功能描述匹配？
3. **范围检查：** 是否聚焦到足以制定单个实现计划，还是需要分解？
4. **歧义检查：** 是否有需求可以被两种方式解读？如果是，选择一种并明确标注

发现问题直接内联修复。无需重新审阅——修复后继续推进。

### 8. 用户审阅 Gate

规格自审通过后，请用户审阅：

> "规格文档已写入并提交到 `<path>`。请审阅，如有需要变更请告知，之后我们再开始制定实现计划。"

等待用户回复。如果请求变更，做出修改并重新自审。**仅在用户批准后继续。**

### 9. 过渡到实现

- 调用 writing-plans 技能创建详细实现计划
- **不得调用任何其他技能。writing-plans 是唯一的下一步**

## 核心原则

- **每次只问一个问题** — 不要用多个问题淹没用户
- **尽量选择题** — 比开放式问题更容易回答
- **严格 YAGNI** — 从所有设计中移除不必要的功能
- **探索替代方案** — 始终提出 2-3 种方案后再确定
- **渐进式验证** — 呈现设计，获得批准后再继续
- **保持灵活** — 当某些内容不合理时回头澄清

## 与其他技能的关系

| 上游 | 当前 | 下游 |
|------|------|------|
| 用户需求 | brainstorming | writing-plans |

brainstorming 完成后**只能**进入 writing-plans。不得直接进入实现、TDD 或 subagent 执行。
