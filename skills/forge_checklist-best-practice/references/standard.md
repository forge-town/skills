# 检查清单规范标准

## 什么是合格的 Checklist

Checklist 有两种用途，规范不同：

| 类型 | 所在 Skill | 条目描述对象 |
|---|---|---|
| **规范 Checklist** | `-best-practice` Skill 的 `references/checklist.md` | 代码/文件应满足的规范条件 |
| **操作完成 Checklist** | 动词型 Skill 的 `references/checklist.md` | 操作执行完毕后的验收项 |

---

## 规范 Checklist 写法

### 结构要求

```markdown
# {模块名} 检查清单

## {分类标题}
- [ ] {编号} {条目描述}
  - ✅ 正确示例：{具体代码或文件名}
  - ❌ 错误示例：{具体代码或文件名} → {说明原因}

## Bad Case 确认
- [ ] ❌ 不存在 {反模式描述} 的情况
```

### 条目写法规则

1. **可判定原则**：每条必须能回答 Yes/No，禁止模糊表述
   - ❌ `- [ ] 命名要规范` → 无法判断
   - ✅ `- [ ] 文件名格式为 {feature}Dao.ts（如 usersDao.ts）`

2. **示例强制**：每条规则必须附至少一个正确示例或错误示例
   - ❌ `- [ ] Props 类型已导出` → 无示例
   - ✅ `- [ ] Props 类型已导出（`export type ButtonProps`）`

3. **编号格式**：使用 `{大类}.{小类}` 编号（如 `1.1`、`2.3`）

4. **分类组织**：相关条目归入同一 `## 分类` 节，不超过 8 条/节

5. **Bad Case 节**：必须有 `## Bad Case 确认` 节列出不得出现的反模式

## 操作完成 Checklist 写法

```markdown
# {操作名} 完成清单

执行完毕后逐项确认：

- [ ] {操作步骤1已完成的验收标准}
- [ ] {操作步骤2已完成的验收标准}
- [ ] 输出报告已生成（含通过/错误统计）
```

### 条目写法规则

1. **动作导向**：描述"已完成某事"，而非"应该做某事"
   - ❌ `- [ ] 扫描目录` → 命令式，非验收式
   - ✅ `- [ ] 目标目录已递归扫描（包含所有子文件夹）`

2. **5-8 条为宜**：过长说明操作粒度太细，应拆分

3. **无需分类**：操作 checklist 通常不需要 `##` 分类节

---

## 禁止模式

- ❌ 条目描述使用"应该"、"需要"、"建议"等模糊词
- ❌ 无任何代码示例的纯文字条目
- ❌ 超过 10 条不分组的平铺清单
- ❌ 缺少 Bad Case 确认节（仅适用于规范 Checklist）
