# 查询与输出流程

## 确定范围与连接

从用户当前请求和会话识别工作区、项目、人员、状态、时间范围。能明确继承当前项目时直接查询；不能确定且会影响结果时再澄清，不默认检索全部工作区。

只使用用户自装的 Linear MCP，例如 linear_code_forge_official、linear_fitness_club、linear_tellyn。linear_code_forge_official 虽含 official 仍是用户自装连接。禁止改用 Codex 内置的 mcp__codex_apps__linear；连接不可用时报告具体缺口，不安装、替换或删除连接。先发现实际可用工具、读取参数，再调用。

“还有什么 Issue”默认查目标项目未归档、未完成且未取消的事项；明确要求全部、已完成、某个人或某个状态时，以用户筛选为准。不要用创建日期限制全部剩余事项；“今天完成”应按完成时间和用户时区筛选，不能用 updatedAt 代替 completedAt。

“进行中”若指 In Progress，应按团队的实际状态查询，不能把所有 started 类型（包括 In Review）都当作 In Progress。状态不确定时读取 list_issue_statuses。查询范围若是负责人“我”，使用 me，不能把其他成员当作当前用户。

## 实时查询与完整性

使用 list_issues 的结构化筛选。项目或团队引用不明确时才查列表确认，避免无必要的全量人员、项目和团队发现。

列表至少取 id、uuid（若支持）、title、url、labels、status、statusType、assignee；跨项目时额外取 project、projectId、teamId。仅在分类或简述无法从标题判断时取 description；仅在被问进展或证据时读 comments、PR 等，不把日常清单扩大成验收审计。

读取响应的 structuredContent，或解析文本 JSON。先检查工具错误；非 JSON 的错误文本不能直接当查询结果解析。某字段因精简 fields 而未请求，不等同于它的值为空；按需补查。

所有列表均检查 hasNextPage。为真时用返回的 cursor 顺序续页，保持同一筛选，直到为假。cursor 缺失、重复或查询失败时，不声称已经取全：重试明确失败的只读请求，仍失败则标明已取得范围。不能把接口失败当作“没有 Issue”。

合并后按工作区加 uuid 去重；无 uuid 时按工作区加 Issue 标识去重，再筛选、分组和计数。分页重叠可去重；同一 Issue 的关键字段有冲突时补查 get_issue，不能静默采用任意一条。

默认未完成筛选依据实时 statusType，排除 completed、canceled，以及接口确实返回的 duplicate 类型。未知或缺失类型需补查或明确待核对，不根据标题猜测 Done，也不遗漏未识别状态。

## 按产品一级模块分组

依据该项目实际标签及已确认的模块规则分组，如 Agent、Metadata，而非发况识别、像素比色等细分能力，也不按 Bug、Opt、Feature 作为功能板块。

分组所需标签信息未知时读取该团队 list_issue_labels，必要时读分组定义；父标签组不等于每个项目的模块全集。跨项目先按项目再按各自模块分组。

以实际 labels 字段为准。标题中的 [Agent] 不是实际 Agent 标签。缺模块标签的放“未分类”；匹配多个模块且没有明确主归属规则的放“分类待确认”，保留标签供用户判断。每个 Issue 只出现一次，不靠标题补造标签。已确认的项目专用规则可以定义技术辅助标签与主板块的区别。

只读查询不创建标签、不补标、不改状态、不分配负责人、不写评论。用户另有明确修改授权时，按授权范围另外执行，不能从“查询”推导写入许可。

## 输出格式

开头最多一句交代筛选范围和总数；每个模块用一行加粗名称及数量，其下固定五列表格：

| Issue | 内容 | 类型 | 状态 | 负责人 |
| --- | --- | --- | --- | --- |
| API 返回的真实 Issue 链接 | 简短中文内容 | 实际工作类型标签 | API 状态原名 | 实际 assignee |

类型取实际 labels 中的工作类型，如 Feature、Bug、Opt、Research、Doc。优先按团队 Type 标签组识别；项目另有明确约定的独立类型标签也可使用。类型映射未知时读取 list_issue_labels（含分组），不把 Agent、Metadata 等模块标签当作类型。没有类型标签写“未标注”；出现互相冲突的类型写出实际值并标“待确认”，不擅自挑选。标题中的 [Bug] 不代替实际标签，也不根据问题描述推断类型。

真实输出必须替换上面的说明文字。Issue 链接的显示文字用 COD-xxx 等标识，URL 逐字使用该条记录返回的 url，不从标题拼 slug，不套其他条目的链接。未返回 url 时补查；仍无法取到则显示无链接标识并说明该链接缺失，不伪造。

内容去掉标题中的类型前缀及重复英文翻译，保留主要问题，不改变诉求。不要给标题批量改名。状态保留 In Progress、In Review、Todo、Backlog 等实际值；负责人为空写“未分配”，不能从评论中的 @、创建者或预期评审人推断 assignee。

同组遵从用户指定顺序；没有要求时按 In Progress、In Review、Todo、Backlog 排列，其余状态稳定排在后面；同状态按 Issue 标识排序。项目有其他状态时保留实际名称，不强行改成上述四种。

已确认模块零结果可用一行表示，如“Metadata（元数据）· 当前筛选范围内无事项”。只有完整查询后才写“无”；部分分页失败时显示“尚未完整查询”。不为其他项目预先建立空白模块。

未要求时不加点数、长篇技术证据、附件或冗余注脚。分类缺口等必要限制用一两句说明。不要把 In Review 写成已验收或已解决。

## 输出前核对

模块数值、行数与唯一 Issue 总数应相等，每行链接、类型、状态、负责人都对应同一条记录。报告来自当前请求中的实时查询；若只是对刚查到的同一快照重新排版，可以复用并说明是该次结果，不能冒充新查询。
