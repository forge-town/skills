# 补录流程

## 1. 范围与授权

“补录当前 worktree/本次 PR 的工作”授权在已明确工作区和项目内查重、创建缺失 Issue、补充实际记录，并更新相关 estimate、状态和负责人。正常补录无需再为这三个字段单独确认；前文同范围授权持续有效。仅理解、盘点或起草保持只读，仅更新本技能也不授权执行当前仓库的补录。

只用用户自装的对应 Linear MCP，不使用 Codex 内置 Linear。按真实仓库定位项目；项目或人员归属不唯一时先完成可确定部分，再询问必要信息。不自动创建 Cycle/标签、回填历史完成时间、提交或清理代码、合并 PR、部署或发送其他渠道消息。

## 2. 读取范围与开发者身份

确认 Git 根目录、worktree、分支、HEAD、status，读取 staged/unstaged diff 和相关 untracked 文件，归纳最终变化避免双计。工作区干净时继续检查本会话明确的已提交 PR，不因此停止，也不把 develop → main 中其他历史工作并入本次范围。遵守 AGENTS.md；有 .codegraph 时先用 CodeGraph 理解代码，不自动建索引。

识别新增、修改、删除、重命名与二进制变化，先快照，再排除本次生成的补录报告。按业务结果归组，区分已实现、已验证、未完成。敏感配置、密钥、缓存及构建产物不作为上传证据。

负责人默认设为该 PR 的实际开发者。结合 PR 作者、实际提交和本会话核对自然人身份，再匹配 Linear 用户；当前用户是 PR 开发者时就 assign 当前用户。新建、复用 Issue 都适用，不能因原来未分配就继续留空。不把发布机器人、代提交账号或当前 Git 配置自动当开发者；多人协作按各 Issue 实际开发归属判断，身份确有冲突时再确认。

## 3. 先匹配已有 Issue

在正确项目按业务目标、模块、场景交叉搜索，包括已完成、取消及可查的归档项。分页读全本次查询范围，读取候选正文、Task、评论和交付链接，不能仅凭标题或只查 open。查询不完整时披露缺口，不断言不存在。

将每组归为已有覆盖、部分覆盖、已经记录、没有对应项或匹配不确定。已有覆盖优先复用；独立新增范围单独判断。创建前再搜索一次。同一业务改动只映射一个主计点 Issue，父子和关联项不能重复计时。已 Done 的原工作可以补历史记录；后续新业务不自动重开原事项。

## 4. 核实投入与实际状态

按 [时长规则](effort.md) 将投入唯一分配到各 Issue；优先采用实际计时，缺少计时时默认使用 Git 与会话回顾估算，不再为估算授权提问。两类来源均明确标注。新建和复用都更新原生 estimate，用投入时长替换计划估点，不能仅留评论却保留旧计划值。

| 真实情况 | 目标状态 |
| --- | --- |
| 已实现、必要自验证据通过，且本 Issue 范围无明确剩余工作 | Done |
| 尚有实现、修复或必要验证未完成 | In Progress，写明剩余项 |
| 只有计划、尚未开始 | Backlog/Todo，使用团队现有状态 |
| 当前字段及记录已正确 | 保持，跳过重复写入 |

事后补录无需额外设置 reviewer 通过这一前提；已完成的工作直接 Done。不能因为缺 reviewer 就统一留 In Progress，也不能把所有补录无条件 Done。PR 合并本身不证明整个 Issue 完成；开发范围已完成的 PR 未合并也不自动阻止 Done。原 Issue 包含部署或正式验收时，仍按其真实完成条件判断。

列出拟执行的 Issue、实际内容、时间及来源、原→目标点数、实际状态、PR 开发者→Linear 用户及重复核对结果。本地材料保存在项目根目录 docs/worktree-backfill/本次批次/：snapshot.json、mapping.md、effort.json、正文/评论草稿和 results.json。工作指纹使用 HEAD、路径/内容摘要及时间记录标识，不归档敏感原文。

## 5. 补录或创建

写入前重读工作指纹、Issue 的状态/点数/负责人及最新评论。发现并发改动或他人已补录时重算受影响部分，不覆盖他人的新增工作。

已有项以评论保留实际内容、输入输出、证据、投入及来源；保留原需求和历史。随后按本次结果更新 estimate、状态和 assignee，不能只写评论而遗留过期计划点数、错误状态或空负责人。已记录同一工作时仅修正必要字段，不重复评论或计点。

新建项采用团队现有项目、类型和标签，按 [记录格式](record-format.md) 写业务正文；优化类型用 Opt，不为凑点拆任务。原生点数允许时长得出的 1、2、3 等整数，不套用事前规划的 8/16。先核对工具字段和团队支持范围；不支持时披露限制，不偷偷映射或修改团队估点配置。

项目另有适用正文/附件要求时遵守，但不虚构历史验收。上传证据采用当前自装连接支持的签名上传流程，传输原始字节并回读可访问链接；评论不写本地绝对路径或 file://，不用规格、原型或旧截图冒充当前验证。

## 6. 状态与回读

补录本身不强制 reviewer 交接；另有明确交接要求时再衔接相应验收流程，不能虚构 reviewer 通过。现在按真实完成情况改状态，不回填历史 completedAt 或自动迁移 Cycle。

创建、评论或字段更新超时先回读，确认未生效才重试；连续两次明确失败后保留材料并报告，不重复创建或发表评论。逐项报告部分成功，不宣称事务回滚。

逐条回读正文/评论、estimate、状态、assignee 和证据链接，核对映射与指纹。最终列出新建、复用、跳过重复、待确认及失败，提供真实 Issue 链接、时间来源和实际字段结果；草稿、未写入或回读失败明确说明。
