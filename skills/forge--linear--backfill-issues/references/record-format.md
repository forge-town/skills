# 补录格式

## 已有 Issue 的补录评论

括号内容执行时替换，不伪装成已发生的事实。

```markdown
补录本 Issue 对应的工作。

完成内容：（具体位置、改动和实际业务结果）
实际进度：（已实现／已验证／未完成，及剩余范围）
代码依据：（仓库、PR、base/head、相关改动及批次标识）
工作发生时间：（实际日期或时段；未知则明确未知）
补录日期：（本次真实日期）
开发者与负责人：（经核对的 PR 开发者 → Linear 用户）

| 工作/验收项 | 输入 | 预期输出 | 实际输出 | 证据 | 判定 |
| --- | --- | --- | --- | --- | --- |
| （原 Task/AC） | （具体输入） | （约定答案） | （真实结果或未验证） | （可访问记录） | （实际结论） |

本次投入：（新增时长、范围与来源：实际计时／用户确认／Git+会话回顾估算）
前次已记录：（累计时长及记录标识，不从原 estimate 反推）
累计与计点：（累计秒数÷3600，向上取整；说明历史缺口及覆盖范围）
原生点数变更：（原 estimate → 按投入计算的 estimate，替换计划值）
状态变更：（原状态 → 实际状态，已完成且必要自验通过则 Done）
负责人变更：（原负责人 → 经核对的 PR 开发者）
重复核对：（哪些记录已存在，此次只补了什么）
```

例如原计划 8 点、实际投入 2 小时、工作完成并通过必要检查，则原生 estimate 改为 2、状态 Done、负责人为 PR 开发者。不能只写参考 2 点而保留 8 点，也不要求额外 reviewer 才能补成 Done。原范围仍有未完成项则保留真实进行状态，写明剩余工作；未复测的输出写未验证。

## 没有对应 Issue 时

采用项目现有标题、语言及标签约定，保留适用正文结构：

- 摘要写做什么、从哪开始、怎样算完成。
- 背景写实际场景、问题和影响，可放用户原话、截图及来源；不添加固定“待查明”字段。
- 用户故事用作为、我希望、从而，写清具体预期结果。
- 功能概览、页面定位、流程、交互契约、前端变更、业务规则、技术说明、非目标及参考资料按实际工作填写，不虚构页面。
- Task 按执行顺序写具体工作及验收条件；验收标准明确给定、操作、预期输出，已有验证另写实际输出和证据，不用“测试通过”代替具体答案。

这是事后补录，正文说明实际发生的工作与进度；不伪装成全新未执行计划或全面交付。estimate 写投入折算值，assignee 写 PR 开发者，状态按真实完成情况填写，完成的就是 Done。时间账、指纹与 Agent 日志放补录记录，不混入产品需求正文。
