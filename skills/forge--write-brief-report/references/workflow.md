# 工作简报流程

## 从会话整理实际成果

先按会话取证确定的起止时间与项目范围提取候选，再以业务事项归并。研发之外，设计、调研、文件处理、客户反馈、模型验证、文档整理和项目管理也可作为实际工作，不强制要求 Git 提交。

同一需求可能跨多个 session、分支或重试；根据具体事项、交付物、PR／文件和实际结果合并一次。派生／分叉会话复制的历史不另计成果。目标时段中先失败后修复的事项按最后有证据的状态汇报，保留仍影响使用的限制。没有新变化的旧成果不重复算该时段完成，跨日完成的工作按目标时段内实际完成节点表述。

例如：一个 session 完成简报草稿，另一个 session 修订同一份简报，应合并为一次交付；不能把起草和改名重复算成两项成果。

## 核对完成程度

| 依据 | 可采用的状态 |
| --- | --- |
| 用户提出需求、讨论方案、助手承诺执行 | 已明确需求／已讨论；不能写成实现 |
| 产物已保存、文档写入回读、调研记录已形成 | 已完成对应交付范围；不能扩大为业务落地 |
| 只有本地修改或测试 | 已实现／本地验证，待合并、发布或使用验收 |
| PR 确认合并 | 已合入，仍需区分是否部署 |
| 对应部署记录与版本匹配 | 指定环境已更新；客户验收另行确认 |
| 具体场景实际检查通过 | 该场景已验证，不外推全能力 |
| 仅有助手自述，关键结果缺失或截断 | 补充只读核对，或保留待核实状态 |

技术结果按需要查提交、PR、测试与部署；调研及文档结果按需要读交付文件和外部文档。用户在 session 中明确确认的结果可保留其确认范围。不为写简报重新部署、跑付费模型、修改文件、联系他人或触发业务操作。

不虚构工时、完成比例、效率提升或人员责任；会话时长和消息数量不等于工时及工作量。旧截图、进度口头结论、命令成功不替代所声称的当前线上版本或验收证据。

## 写成汇报正文

日期或起止时间与“工作简报”或用户指定的项目名独占一行；默认当天汇总可用“日报”标题，指定时段须如实展示该范围，正文按“一、二、三、”组织。多项目按项目归并；单项目按实际成果主题分段。用“做了什么、产出什么、现在能做什么”表达，状态和阻塞紧接相关成果，不写工具流水账或会话摘要目录。

默认用简洁纯文本，可直接转发到工作群。正文不使用 Markdown 标题、加粗、代码反引号、项目符号或表格；不强行凑三项，也不把细碎操作拆成多项功劳。普通简报可从 300—600 字起，根据实际事项调整；单一小事项可更短。用户有格式要求时以其要求为准。

优先讲功能、体验、调研结论、资料交付和项目进度，省略不影响理解的框架名、数据库、内部架构、命令、PR 编号等；技术日报才展开技术细节。用户纠正的需求、反馈与已实施结果分清，不将意见本身写成已经落地。

默认不附后续计划；用户明确要求时再补。待发布、待核实、待验收直接写在对应事项中。来源链接和会话 ID 留在核验记录，除非用户要求在正文展示。

## 交付与范围说明

通常在当前对话交付完整可用正文。若未覆盖用户要求的全部会话、来源或时间，应在正文外简短说明实际覆盖范围，不能把“读到三个 session”说成“指定时段的全部工作”。上下文或工具不足时照实交付可确认的部分。

用户要求文件或确有保留价值时，正文保存到项目 docs/reports/brief-reports/。单日文件使用 YYYY-MM-DD-brief-report.txt；时段简报使用包含起止日期或时刻的文件名，同目录另存核验记录；多项目或同日多次输出增加项目/批次标识，避免覆盖。

核验记录写明项目与会话范围、起止时间、时区、实际核验截止时刻、已读 session 的真实 ID／标题、分页覆盖、直接结果和未核实边界。不保存内部思考、凭据、完整客户原话或大段无关聊天，必要链接脱敏。

默认只交付正文。用户另行要求发送或发布时，先准备可核对的简报，再按该次明确授权选择实际可用工具；不依赖未收录的飞书管理技能，不从“写简报”推导外部写入或持续监控权限。
