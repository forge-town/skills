## 命名规范

### 1.1 目录名命名规则
**检查项**：目录名是否符合命名规范

**通过标准**：
- 不包含 `-skill` 后缀
- 仅使用英文小写字母（a-z）
- 使用连字符（`-`）分隔单词
- 首字符为小写字母
- 不包含空格、下划线、大写字母或特殊字符

**示例**：
- ✅ 正确：`pdf-parser`, `image-processor`, `web-scraper`
- ❌ 错误：`pdf-parser-skill`, `PDF_Parser`, `PdfParser`, `pdf parser`

**检查方法**：
1. 查看 Skill 目录名称
2. 验证是否符合正则表达式 `^[a-z][a-z0-9-]*$`
3. 确认不以 `-skill` 结尾

### 1.2 打包文件名一致性
**检查项**：打包文件名与目录名是否一致

**通过标准**：
- 打包文件名应为 `<skill-name>.skill`
- `<skill-name>` 部分与目录名完全一致

**示例**：
- ✅ 正确：目录 `pdf-parser/` → 打包为 `pdf-parser.skill`
- ❌ 错误：目录 `pdf-parser/` → 打包为 `pdf-parser-v2.skill`

## SKILL.md 前言区

### 2.1 name 字段
**检查项**：name 字段存在且符合规范

**通过标准**：
- name 字段存在于前言区（YAML 部分）
- name 值与 Skill 目录名完全一致
- name 值符合命名规范（同 1.1）

**检查方法**：
1. 打开 `SKILL.md`
2. 读取 `---` 之间的 YAML 前言区
3. 验证 `name` 字段存在
4. 对比 `name` 值与目录名

### 2.2 description 字段
**检查项**：description 字段存在且符合格式

**通过标准**：
- description 字段存在于前言区
- description 为单行文本（不包含换行符）
- 长度在 100-150 字符之间
- 包含 Skill 的核心能力
- 包含典型触发场景（可列举多个互不耦合的场景）

**示例**：
```
description: 批量处理PDF文档；支持文本提取、格式转换、元数据管理；适用于文档分析和内容整理场景
```

**检查方法**：
1. 验证 `description` 字段存在
2. 检查是否包含换行符
3. 统计字符长度
4. 验证内容包含核心能力和触发场景

### 2.3 dependency 字段（可选）
**检查项**：dependency 字段格式正确（如果存在）

**通过标准**：
- `dependency.python` 为列表格式，每个元素遵循 requirement.txt 格式
- `dependency.system` 为列表格式，每个元素为有效的命令行命令
- 不在 dependency 中包含 Python 包安装命令（应在 python 字段中）

**示例**：
```yaml
dependency:
  python:
    - requests==2.28.0
    - pandas>=1.5.0
  system:
    - mkdir -p input-data
```

**检查方法**：
1. 检查 `dependency` 字段是否为字典类型
2. 验证 `python` 字段（如果存在）为列表，且每个元素符合 `package==version` 或 `package>=version` 格式
3. 验证 `system` 字段（如果存在）为列表，且每个元素为有效命令

## 目录结构

### 4.1 固定结构符合性
**检查项**：目录结构符合固定结构要求

**通过标准**：
- 必须包含：`SKILL.md`
- 可选包含：`scripts/`, `references/`, `assets/`（这些目录不存在时不报错）
- 不存在额外的文件或文件夹（如 `README.md`, `tmp/`, `.cache/` 等）

**重要说明**：
- `scripts/`, `references/`, `assets/` 是可选目录
- 如果 Skill 不需要脚本，可以没有 `scripts/` 目录
- 如果 Skill 不需要参考文档，可以没有 `references/` 目录
- 如果 Skill 不需要静态资源，可以没有 `assets/` 目录
- **仅包含上述四种类型，不能有其他文件或文件夹**

**示例**：
- ✅ 正确 1：仅包含 `SKILL.md`（最简单的 Skill）
- ✅ 正确 2：包含 `SKILL.md` + `scripts/`
- ✅ 正确 3：包含 `SKILL.md` + `scripts/` + `references/` + `assets/`
- ❌ 错误：包含 `SKILL.md` + `scripts/` + `README.md`（多了 README.md）

### 4.2 空目录检查
**检查项**：不包含空目录

**通过标准**：
- `scripts/` 如果存在，必须包含至少一个文件
- `references/` 如果存在，必须包含至少一个文件
- `assets/` 如果存在，必须包含至少一个文件
- **如果这些目录不存在，不报错（因为它们是可选的）**

**检查方法**：
1. 检查 `scripts/`, `references/`, `assets/` 是否存在
2. 对于存在的目录，验证其内容不为空
3. 对于不存在的目录，标记为通过（可选目录，无需强制存在）

### 4.3 引用路径正确性
**检查项**：路径引用符合工作环境定义

**通过标准**：
- SKILL.md 中引用脚本时使用相对路径 `scripts/xxx.py`
- 脚本中引用 Skill 内文件时使用相对于 Skill 根目录的路径
- 脚本中引用用户文件时使用 `./` 相对路径

**检查方法**：
1. 检查 SKILL.md 中的路径引用格式
2. 检查脚本中的路径引用格式
3. 验证路径能够正确解析到预期文件

## 实现方式合理性

### 5.1 脚本使用符合选型指南
**检查项**：脚本的必要性验证

**通过标准**：
- 文件格式处理（docx/pdf/Excel转换、图片压缩等）使用了脚本
- 外部API调用（需要鉴权的第三方服务、复杂API工作流）使用了脚本
- 复杂数据计算（数学统计、算法实现、大规模数据处理）使用了脚本
- 内容创作、知识咨询、分析推理类任务未使用脚本（由智能体自然语言处理）
- 图像识别、生成类任务未使用脚本（由智能体原生能力处理）

**检查方法**：
1. 检查 `scripts/` 目录中的脚本功能
2. 分析每个脚本的业务逻辑
3. 验证脚本处理的是技术性任务而非智能体可完成的任务
4. 确认没有为简单任务（如"生成大纲"、"格式化文本"）编写脚本

### 5.2 脚本必要性
**检查项**：每个脚本都有明确的技术性理由

**通过标准**：
- 脚本的功能无法通过智能体的自然语言能力完成
- 脚本处理的是文件系统操作、结构化数据、第三方API等技术性问题
- 不存在"为创作类任务编写生成器"的情况

**检查方法**：
1. 逐个分析脚本的功能描述
2. 验证每个脚本都有技术性理由
3. 确认没有随机生成、创意生成等非技术性脚本

## 脚本质量

### 6.1 语法正确性
**检查项**：脚本语法正确

**通过标准**：
- Python 脚本可以通过语法检查
- 无语法错误、缩进错误、未闭合的括号等

**检查方法**：
1. 尝试编译脚本
2. 检查是否有语法错误

### 6.2 架构合规性
**检查项**：脚本为纯函数式工具

**通过标准**：
- 不包含 Web Server（Flask/FastAPI 等）
- 不包含持久化服务、守护线程、常驻内存
- 不包含交互式循环或命令行菜单
- 不监听端口、不提供 HTTP 接口
- 脚本作为纯函数被调用：接收参数 → 处理数据 → 返回结果

**检查方法**：
1. 检查脚本是否导入 Flask、FastAPI 等 Web 框架
2. 检查是否有 `app.run()`, `uvicorn.run()` 等启动服务的代码
3. 检查是否有 `while True` 等持久循环
4. 验证脚本的核心逻辑是函数调用而非服务启动

### 6.3 依赖规范
**检查项**：依赖清晰且符合规范

**通过标准**：
- 脚本依赖已明确列在 `dependency.python` 中
- 使用标准库或常用第三方库
- 如果涉及第三方 API 调用，从 `coze_workload_identity` 导入 requests 或 httpx
- 所有凭证通过 `os.getenv()` 从环境变量读取

**检查方法**：
1. 分析脚本的 import 语句
2. 验证第三方库已在 dependency 中声明
3. 检查网络请求是否使用 `coze_workload_identity.requests`
4. 验证凭证获取方式

### 6.4 参数规范
**检查项**：参数定义清晰

**通过标准**：
- 脚本通过参数接收所有动态变量
- 不在脚本中设置硬编码的占位符让调用方替换
- 函数参数有明确的用途说明（通过文档字符串或注释）

**检查方法**：
1. 检查脚本函数的参数列表
2. 验证没有类似 `# TODO: 替换为实际 API_KEY` 的占位符
3. 检查是否有参数说明文档

### 6.5 第三方 API 授权处理
**检查项**：涉及第三方 API 调用时，授权处理符合规范

**通过标准**：
- 如果脚本调用第三方 API 且需要授权，已按"脚本调用第三方服务"流程处理
- 凭证通过 `os.getenv("COZE_<credential_name>_<skill_id>")` 读取
- 不在脚本中硬编码凭证
- 不在脚本参数中传递凭证

**检查方法**：
1. 检查脚本是否调用第三方 API
2. 验证 API 调用是否需要授权
3. 检查授权处理方式是否符合规范

## 常见问题

### Q1: 如果某些检查项不适用怎么办？
A: 对于可选检查项（如 dependency 字段、scripts/、references/、assets/ 目录），如果相关内容不存在，则该检查项自动通过。智能体在检查时应识别出这些是"可选"的，不将其标记为失败。

### Q2: 如何判断脚本是否必要？
A: 参照"实现方式合理性"章节，核心原则是：智能体能完成的任务不应编写脚本。脚本只用于文件格式处理、第三方API调用、复杂数据计算等技术性操作。

### Q3: scripts/、references/、assets/ 目录是必需的吗？
A: 不是必需的。这些目录是可选的：
- `scripts/`：仅当 Skill 需要技术性脚本时才存在
- `references/`：仅当 Skill 需要长篇参考文档时才存在
- `assets/`：仅当 Skill 需要静态资源（模板、图标等）时才存在
- 最简单的 Skill 可以只包含 `SKILL.md` 文件

### Q4: 为什么会出现"缺少必需的 scripts/ 目录"的错误？
A: 这是错误的检查结果。scripts/、references/、assets/ 是可选目录，不应该报告为"缺少必需的"。如果智能体报告此类错误，说明检查逻辑有问题，应修正为：这些目录不存在时标记为通过（而非失败）。

### Q5: 临时文件应该如何处理？
A: 在打包前必须清理所有临时文件和缓存。建议在开发过程中避免生成临时文件，或及时清理。

### Q6: 如果检查不通过怎么办？
A: 根据检查报告中的具体问题描述，参考"问题修复指南"章节，逐项修复后重新检查。

## 问题修复指南

### 修复原则
- 优先使用自动修复：对于可自动修复的问题，智能体直接执行修复操作
- 需要人工确认：对于涉及业务逻辑或设计决策的问题，先提供修复建议，等待用户确认
- 备份优先：执行任何修改操作前，先确认修改的正确性

### 常见问题修复方法

#### 1. 命名规范问题

**问题描述**：
- 目录名包含 `-skill` 后缀
- 目录名使用大写字母、下划线或空格

**修复方法**：
1. 对于 `-skill` 后缀问题：重命名目录，移除后缀
   ```bash
   mv my-skill-skill my-skill
   ```
2. 对于命名格式问题：重命名目录为小写字母+连字符
   ```bash
   mv MySkill my-skill
   mv my_skill my-skill
   ```

**注意事项**：
- 需要同时更新 SKILL.md 中的 name 字段
- 需要更新其他引用该目录的路径
- 建议先询问用户是否同意重命名

---

#### 2. SKILL.md 前言区问题

**2.1 name 字段缺失或不匹配**
**问题描述**：
- 前言区缺少 name 字段
- name 字段与目录名不一致

**修复方法**：
1. 读取 SKILL.md 前言区
2. 如果 name 缺失，添加：`name: <目录名>`
3. 如果 name 不匹配，修改为正确的目录名

**示例**：
```yaml
---
name: my-skill
description: ...
---
```

---

**2.2 description 长度不符合要求**
**问题描述**：
- description 长度 < 100 字符或 > 150 字符

**修复方法**：
1. 分析现有 description 的核心内容
2. 重写 description，使其满足：
   - 包含 Skill 的核心能力
   - 包含典型触发场景
   - 长度控制在 100-150 字符
3. 保持原意的基础上进行优化

**示例**：
```
原描述：检查Skill规范（15字符，太短）

修复后：批量检查Skill是否符合最佳实践规范；验证命名、格式、结构等维度；生成检查报告（68字符，仍不足）

最终修复：批量检查Skill是否符合最佳实践规范；自动验证命名、格式、结构、脚本质量等维度；生成详细检查报告；适用于Skill质量验证场景（102字符，符合要求）
```

**2.3 dependency 格式错误**
**问题描述**：
- dependency.python 不是列表格式
- dependency.system 不是列表格式
- 包含 Python 包安装命令

**修复方法**：
1. 检查 dependency 字段的格式
2. 修正为列表格式
3. 将 Python 包安装命令移至 python 字段

**示例**：
```yaml
# 错误格式
dependency:
  python: requests==2.28.0  # 应为列表
  system: "mkdir -p data"   # 应为列表

# 正确格式
dependency:
  python:
    - requests==2.28.0
  system:
    - mkdir -p data
```

#### 5. 脚本质量问题

**5.1 脚本语法错误**
**问题描述**：
- Python 脚本存在语法错误

**修复方法**：
1. 运行语法检查，定位错误位置
2. 修正语法错误（缩进、括号、引号等）
3. 重新运行检查确认修复成功

**命令示例**：
```bash
python -m py_compile scripts/check.py
```

---

**5.2 脚本架构不符合要求**
**问题描述**：
- 脚本包含 Web Server（Flask/FastAPI）
- 脚本包含持久服务或交互循环

**修复方法**：
1. 移除 Web Server 代码（app.run()、uvicorn.run() 等）
2. 移除持久循环（while True）
3. 将脚本改为纯函数式工具：
   - 定义函数接收参数
   - 执行处理逻辑
   - 返回结果

**示例**：
```python
# 错误：Web Server
from flask import Flask
app = Flask(__name__)
@app.route('/')
def hello():
    return "Hello"
app.run()

# 正确：纯函数式
def process_data(data: str) -> str:
    """处理数据并返回结果"""
    return data.upper()
```

**5.3 脚本依赖不符合规范**
**问题描述**：
- 使用标准库 requests 而非 coze_workload_identity.requests
- 凭证硬编码而非从环境变量读取

**修复方法**：
1. 修改 import 语句
2. 修改凭证获取方式

**示例**：
```python
# 错误
import requests
api_key = "your-api-key"  # 硬编码

# 正确
from coze_workload_identity import requests
import os
api_key = os.getenv("COZE_CREDENTIAL_NAME_1234567890")  # 从环境变量读取
```

### 修复模式

#### 自动修复模式
适用于可以安全自动修复的问题：
- 删除临时文件和缓存
- 删除空目录
- 修正简单的格式错误（如 indentation）
- 添加缺失的简单字段（如 name 字段）

#### 人工确认模式
适用于需要判断的问题：
- 重命名目录（影响范围大）
- 修改 description（涉及业务表达）
- 删除可能需要保留的文件
- 修改脚本逻辑（可能影响功能）

### 修复后验证
执行任何修复操作后，必须：
1. 重新运行检查
2. 确认问题已解决
3. 确认没有引入新问题
4. 生成修复报告
