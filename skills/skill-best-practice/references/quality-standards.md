## 命名规范说明

### 为什么使用小写字母和连字符？
- **兼容性**: 避免不同操作系统对大小写处理的差异（Windows 不区分大小写，Linux/Mac 区分）
- **可读性**: 连字符比下划线更易于阅读和记忆（如 `exam-grading` vs `exam_grading`）
- **URL 友好**: 连字符在 URL 中更友好（SEO 优化）

### 为什么禁止 `-skill` 后缀？
- **避免冗余**: 打包后的文件名为 `.skill`，如 `exam-grading.skill`
- **清晰性**: 目录名应反映功能而非类型（如 `exam-grading` 而非 `exam-grading-skill`）

### 何时使用 `-best-practice` 后缀？
- **适用范围**: 仅用于最佳实践检查、规范验证类的 Skill
- **命名约定**: `<领域>-best-practice`（如 `skill-best-practice`, `code-style-best-practice`）
- **避免滥用**: 普通 Skill 不应使用此后缀

## 目录结构说明

### 为什么采用固定结构？
- **标准化**: 统一的结构让智能体更容易理解和使用 Skill
- **最小化**: 仅包含必要目录，避免冗余和混乱
- **可预测**: 用户可以快速定位资源（scripts/references/assets）

### 为什么禁止 README.md？
- **入口统一**: SKILL.md 作为唯一的入口文档
- **避免混淆**: 多个入口文档会导致信息分散和版本不一致
- **遵循惯例**: Skill 的使用方式与传统项目不同（无独立用户界面）

### 为什么禁止临时文件？
- **打包纯净**: 打包时不应包含缓存和临时文件
- **减小体积**: 临时文件会无谓增加 .skill 文件大小
- **避免版本污染**: .gitignore 文件不应出现在 Skill 中

## SKILL.md 前言区说明

### 为什么需要 YAML 前言区？
- **机器可读**: 智能体可以轻松解析元数据（name、description、dependency）
- **渐进式披露**: 前言区始终加载，正文在需要时加载，节省上下文
- **结构化**: 便于自动化工具处理和管理 Skill

### 为什么 description 要有长度限制？
- **上下文效率**: 100-150 字符足以描述核心价值，避免冗余
- **可读性**: 过长的描述会占用宝贵的上下文空间
- **聚焦核心**: 迫使提炼最关键的信息（核心能力+触发场景）

### 为什么依赖要分离为 python 和 system？
- **职责分离**:
  - `python`: Python 包依赖，可通过 pip 安装
  - `system`: 系统级命令（mkdir、chmod 等），不属于包管理范围
- **避免混乱**: 将所有依赖混在一起会导致维护困难
- **自动化友好**: 便于不同的安装脚本分别处理

## 文件清理说明

### 为什么必须清理缓存文件？
- **可移植性**: 缓存文件与运行环境相关，不应打包
- **一致性**: 避免不同环境生成的缓存文件差异
- **安全性**: 缓存文件可能包含敏感信息（如 token、密钥）

### 常见缓存文件模式
- **Python**: `__pycache__/`, `*.pyc`, `.pytest_cache/`
- **macOS**: `.DS_Store`
- **Windows**: `Thumbs.db`
- **临时目录**: `tmp/`, `temp/`, `.cache/`

## 检查级别说明

### pass（通过）
- **含义**: 完全符合规范
- **处理**: 无需任何操作

### warning（警告）
- **含义**: 建议修复但不影响核心功能
- **示例**:
  - description 长度略超或略低于推荐范围
  - 存在不影响运行的空目录
- **处理**: 根据具体情况决定是否修复

### error（错误）
- **含义**: 违反强制规范，必须修复
- **示例**:
  - 缺少必需字段（name、description）
  - 存在不符合规范的文件（README.md）
  - 命名不符合规范
- **处理**: 必须修复后才能通过检查
