# 证据与结论规则

## 覆盖与比较

每项沿用原 AC/Task 编号，记录具体输入、给定的当前必要状态、预期输出、本次操作、实际输出与证据。语音、图片或文件要能定位到固定样本；“符合资料”“正常工作”不足以作为标准答案。

原标准缺具体预期时先列出缺口，请原需求确认方补充；不要照实际结果倒填答案，也不要临时增加原范围以外的验收门槛。

结果判定：

| 条件 | 单项判定 |
| --- | --- |
| 明确预期，当前版本真实结果满足 | 通过 |
| 明确预期，实际结果存在具体差异 | 未通过 |
| 缺设备/凭据/样本/核定答案，或版本无法对应 | 未验证 |
| 截图、报告及复测之间冲突，原因未查清 | 未验证，说明冲突 |

只要有未通过项，整体验收结论为“未通过”，同时保留其他未验证项。没有未通过但有未验证项，结论为“复核未完成”。全部约定项通过，且本次由实际 reviewer 或其已明确授权的 Agent 执行复核，才能给最终“通过”。若仍需指定的人类 reviewer 确认，写“复核未完成：Agent 复测通过，待指定 reviewer 确认”，不能代为签署最终通过结论。

## 证据强度与复测

对用户操作和端到端 AC，在指定或已确认的环境、端和实际版本复测。提交人日志、PR、单元测试、模拟回执只能支持其真正覆盖的环节。例如微信端 AC 要求图片收到且可打开，本地 UI 显示图片与发送接口返回成功都不能代替手机验证。

文档或 Research 任务核对实际产物与约定范围、事实来源、方法和结论；不强行套用浏览器测试。合适且可复现的自动化报告可以作为证据，需核对其版本、运行范围和真实结果，不为形式重复同等有效的检查。

不能运行的验证明确标记，已经核实的证据也如实写清，例如“已核对现有报告，未在手机复测”。不能把当前不能复测等同于所有历史证据无效，但不能声称自己执行过。

截图/录屏核对画面、输入、输出、来源、时间和环境，附件打开不等于内容正确。过期签名链接可通过原评论重新获取；仍无法访问则记录证据缺口，不猜测内容。

## 版本变化与反馈

复核中版本发生变化时，记录每项实际使用的版本。只有确认同一最终版本覆盖全部 AC，或有明确证据说明变化不影响对应验收项，才能给当前版本完整通过结论；相关行为被改动则重跑受影响项。

reviewer 发现新增需求时单独列为范围建议，不据此否决满足原约定的功能，不自动新建 Issue。原范围内差异写明 AC、输入、预期、实际和证据，交由提交人修复；本技能不偷偷修改被测实现。
