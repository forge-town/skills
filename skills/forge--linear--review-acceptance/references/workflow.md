# 验收复核流程

## 范围与授权

“看看证据”“起草意见”“只复测不评论”只产生本地结果。明确要求完成 reviewer 验收流程、回评或按流程关闭时，已有授权涵盖对应 Issue 的复核证据上传、结论评论及符合条件的状态变更，无需重复确认。

创建本技能本身不授权修改真实 Linear。不要创建新 Issue、修改原规格/估点/负责人、合并 PR、部署代码或发送其他渠道消息。

只使用用户自装的对应 Linear MCP，例如 linear_code_forge_official、linear_fitness_club、linear_tellyn；不得改用 Codex 内置 Linear，也不安装、移除或替换连接。

## 读取目标与当前交接

通过当前工具发现核对参数，读取目标 Issue 的正文、Task/AC、团队状态、当前状态、相关附件及完整评论。分页读取到结束；若资料不全就列明覆盖范围。

定位最新一次提交验收的评论及其版本、环境和范围。用实际版本与关联关系确定本次交接，不机械采用“最新一条评论”，也不把旧版本的通过结论用于新改动。

reviewer 取本次或当前会话明确指派、Issue 明确评审关系或已确认团队规则，并核对实际成员。assignee、创建者及评论里偶然出现的人不自动等于 reviewer。Agent 执行复测时如实写执行身份，不把“Agent 复测通过”写成“某位同事已验收”。

若用户已明确把本次 reviewer 职责委托给当前 Agent，可按该委托给出复核结论；若仍要求指定的人类 reviewer 确认，Agent 只提供复测记录并提交给该人，不能代签或转 Done。身份不明确时先完成可执行的复测与草稿，再询问缺失信息。

## 独立验证

以原 AC 以及 Task 的独立验收条件建立覆盖清单。逐条核对提交人的输入、预期、实际输出、证据及环境/版本；对照证据内容，不把附件数量或“已通过”声明作为通过依据。

按 assessment.md 执行本次复测。具备当前授权、设备、凭据和资料的验证直接执行；涉及真实支付、不可逆操作或额外业务权限时遵守原有权限要求，不因验收请求扩大授权。

本地输入、记录和证据放在实际项目根目录 docs/acceptance-review/Issue编号/本次批次/。保存足以复核的真实结果，区分原提交证据与本次复核证据。不要生成假截图或用规格讲解视频证明实际功能通过。

## 回评

只读任务交付本地结论。获授权回评时，按模板生成一条完整评论，逐项给出输入、预期、实际输出、证据和判定；失败项说明具体差异与复现方法，缺项写“未验证”。

需要图片或文件时用对应连接的评论上传工具，逐个申请短效地址、PUT 原始字节、嵌入返回的 Markdown；不把本地路径或 base64 当作 Linear 证据。可访问的现有证据可以直接引用。

获授权通知提交人时提及已核实成员；不任意 @ 项目全员。不覆盖提交人评论或旧评审结论，新一轮复核使用新评论保留历史。

发布后回读评论，核对目标、版本、结论、证据和真实提及。不能验证通知投递时只报告“评论已提及”，不声称对方已收到。

超时或结果不确定时先回读同版本、同批次评论，确认未发布才重试；连续两次明确失败后保留本地成果并报告，不重复刷评论。

## 状态与结束条件

评论确认无误后才变更状态，并回读 Issue：

- 通过：原范围全部满足，当前版本明确，实际 reviewer 身份/委托明确，且授权包含流程关闭，才能转团队的 Done。
- 未通过：评论指出不符合的 AC；有原有团队规则及当前授权时转 In Progress，否则保持现状并报告。
- 未完成复核：存在未验证或结论冲突时保持 In Review，不标 Done，也不把资料不足直接判成产品缺陷。
- 部分通过：仅描述已通过项；整条 Issue 不关闭。

Issue 已 Done/Canceled 时先报告状态；未经明确授权不重开。若本轮目标已被其他人改动或新提交替换，重新核对范围和版本，不覆盖他人的有效状态。

回评成功但状态变更失败时分别报告，补状态不重发评论。最后提供真实 Issue/评论链接、结论、逐项结果和缺口。没有 comment URL 时给真实 Issue URL 与评论 ID，不拼造链接。完成本轮后停止；持续跟踪需用户另行要求，不创建自动提醒。
