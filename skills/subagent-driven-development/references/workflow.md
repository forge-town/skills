# Subagent-Driven-Development 工作流详解

## 何时使用

```
有实现计划？
  ├── 是 → 任务大多独立？
  │         ├── 是 → 在当前会话中？
  │         │         ├── 是 → subagent-driven-development ✓
  │         │         └── 否 → 内联执行
  │         └── 否（强耦合）→ 手动执行或先回 brainstorming
  └── 否 → 先用 brainstorming + writing-plans
```

**vs. 内联执行：**
- 同一会话（无上下文切换）
- 每个任务全新子代理（无上下文污染）
- 每个任务后双阶段审查：先规格一致性，后代码质量
- 更快迭代（任务间无需人工介入）

## 执行流程

```
读取计划，一次性提取所有任务全文 + 上下文，创建 TodoList
    ↓
┌─── 对每个任务 ───────────────────────────────────────────┐
│                                                           │
│  分派实现子代理（附完整任务文本 + 上下文）                    │
│      ↓                                                    │
│  子代理有问题？─── 是 → 回答问题，提供上下文 → 重新分派      │
│      ↓ 否                                                 │
│  子代理实现、测试、提交、自审                                │
│      ↓                                                    │
│  分派规格审查子代理                                         │
│      ↓                                                    │
│  规格一致？─── 否 → 实现子代理修复 → 重新审查                │
│      ↓ 是                                                 │
│  分派代码质量审查子代理                                     │
│      ↓                                                    │
│  质量通过？─── 否 → 实现子代理修复 → 重新审查                │
│      ↓ 是                                                 │
│  标记任务完成                                              │
│                                                           │
└─── 还有任务？─── 是 → 下一个任务 ──────────────────────────┘
         ↓ 否
分派最终代码审查子代理（审查整体实现）
         ↓
完成
```

## 模型选择

使用**能胜任角色的最低能力模型**以节省成本并提升速度。

**机械性实现任务**（隔离函数、明确规格、1-2 个文件）：使用快速便宜模型。计划写得好时，大多数实现任务都是机械性的。

**集成与判断任务**（多文件协调、模式匹配、调试）：使用标准模型。

**架构、设计和审查任务**：使用最强大的可用模型。

**任务复杂度信号：**
- 涉及 1-2 个文件且有完整规格 → 便宜模型
- 涉及多个文件且有集成关注 → 标准模型
- 需要设计判断或广泛的代码库理解 → 最强模型

## 子任务分派模板

每次分派必须包含：

- **任务 ID 与目标描述**
- **完整任务文本**（从计划中提取，不让子代理自己去读计划文件）
- **场景设定上下文**（此任务在整体中的位置、前置任务产出了什么）
- **允许修改的文件**
- **禁止修改的文件**
- **必须通过的验证命令**
- **输出格式要求**

## 处理子代理状态

子代理报告四种状态之一，分别处理：

**DONE：** 进入规格一致性审查。

**DONE_WITH_CONCERNS：** 子代理完成了工作但标记了疑虑。在继续前阅读疑虑。如果涉及正确性或范围，在审查前处理。如果只是观察性意见（如"这个文件变大了"），记录后继续审查。

**NEEDS_CONTEXT：** 子代理需要未提供的信息。提供缺失上下文并重新分派。

**BLOCKED：** 子代理无法完成任务。评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并用同模型重新分派
2. 如果任务需要更强推理，用更强模型重新分派
3. 如果任务太大，拆分为更小的部分
4. 如果计划本身有问题，升级给人工

**永远不要**忽略升级或强迫同一模型无变更重试。如果子代理说它卡住了，某些东西需要改变。

## 双阶段审查

### 阶段一：规格一致性审查

分派规格审查子代理检查：
- 是否严格满足原设计与任务目标
- 是否存在**遗漏**的需求
- 是否存在**多余**的未要求功能
- 规格审查未通过 = 未完成

### 阶段二：代码质量审查

**必须在规格一致性通过之后才能开始。** 分派代码质量审查子代理检查：
- 类型安全
- 安全性
- 可读性与可维护性
- 测试充分性
- 性能考量

不通过则实现子代理修复，审查子代理重新审查。重复直到通过。

## 红旗

**永远不要：**
- 未经用户明确同意就在 main/master 分支开始实现
- 跳过审查（规格一致性或代码质量）
- 在问题未修复时继续推进
- 并行分派多个实现子代理（会冲突）
- 让子代理自己读计划文件（提供完整文本）
- 跳过场景设定上下文（子代理需要理解任务在整体中的位置）
- 忽略子代理的问题（回答后再让他们继续）
- 在规格一致性方面接受"差不多"（审查发现问题 = 未完成）
- 跳过审查循环（审查发现问题 = 实现修复 = 再次审查）
- 让实现子代理的自审替代正式审查（两者都需要）
- **在规格一致性 ✅ 之前开始代码质量审查**（顺序错误）
- 在任一审查有未解决问题时移动到下一个任务

**如果子代理提问：**
- 清晰完整地回答
- 必要时提供额外上下文
- 不要催它们赶紧开始实现

**如果审查发现问题：**
- 实现子代理（同一个）修复
- 审查子代理重新审查
- 重复直到通过
- 不要跳过重新审查

**如果子代理任务失败：**
- 分派修复子代理并给出具体指令
- 不要手动修复（上下文污染）

## 优势

**vs. 手动执行：**
- 子代理自然遵循 TDD
- 每个任务全新上下文（无混淆）
- 并行安全（子代理不互相干扰）
- 子代理可以提问（工作前和工作中都可以）

**效率提升：**
- 无文件读取开销（controller 提供完整文本）
- Controller 精确策划需要什么上下文
- 子代理一开始就获得完整信息
- 问题在工作开始前浮出（不是之后）

**质量门禁：**
- 自审在交接前捕获问题
- 双阶段审查：规格一致性 → 代码质量
- 审查循环确保修复真的有效
- 规格一致性防止过度/不足实现
- 代码质量确保实现质量

**成本：**
- 更多子代理调用（每个任务 1 实现 + 2 审查）
- Controller 做更多准备工作（预先提取所有任务）
- 审查循环增加迭代
- 但早期发现问题（比事后调试便宜）
