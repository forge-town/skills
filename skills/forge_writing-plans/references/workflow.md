# Writing-Plans 工作流详解

## 范围检查

如果规格覆盖了多个独立子系统，它应该在 forge_brainstorming 阶段就被拆分为子项目规格。如果没有，建议拆分为独立计划——每个子系统一个计划。每个计划应该能独立产出可工作、可测试的软件。

## 文件结构规划

在定义任务之前，先映射出哪些文件将被创建或修改，以及每个文件的职责。这是分解决策被锁定的地方。

- 设计边界清晰、接口定义良好的单元。每个文件应有一个明确职责
- 你对能一次放进上下文的代码推理效果更好，文件越聚焦编辑越可靠。优先选择更小、更聚焦的文件
- 一起变更的文件应该放在一起。按职责拆分，不按技术层拆分
- 在现有代码库中,遵循已有模式。如果你要修改的文件已经变得难以管理，在计划中包含拆分是合理的

此结构指导任务分解。每个任务应产出独立有意义的、自包含的变更。

## 任务粒度：一口大小

**每步是一个动作（2-5 分钟）：**
- "编写失败测试" — 一步
- "运行测试确认失败" — 一步
- "实现最小代码使测试通过" — 一步
- "运行测试确认通过" — 一步
- "提交" — 一步

## 计划文档头部模板

**每个计划必须以此头部开始：**

```markdown
# [功能名称] 实现计划

> **执行指引：** 推荐使用 forge_subagent-driven-development 技能逐任务执行此计划。
> 步骤使用 checkbox (`- [ ]`) 语法追踪进度。

**目标：** [一句话描述此计划构建什么]

**架构：** [2-3 句话描述技术方案]

**技术栈：** [关键技术/库]

---
```

## 任务结构模板

````markdown
### Task N: [组件名称]

**文件：**
- 新建: `exact/path/to/file.ts`
- 修改: `exact/path/to/existing.ts:123-145`
- 测试: `tests/exact/path/to/test.ts`

- [ ] **Step 1: 编写失败测试**

```typescript
test('具体行为描述', () => {
  const result = targetFunction(input)
  expect(result).toBe(expected)
})
```

- [ ] **Step 2: 运行测试确认失败**

运行: `bun test tests/path/test.ts`
预期: FAIL — "targetFunction is not defined"

- [ ] **Step 3: 编写最小实现**

```typescript
export function targetFunction(input: InputType): OutputType {
  return expected
}
```

- [ ] **Step 4: 运行测试确认通过**

运行: `bun test tests/path/test.ts`
预期: PASS

- [ ] **Step 5: 提交**

```bash
git add tests/path/test.ts src/path/file.ts
git commit -m "feat: add specific feature"
```
````

## 严禁占位符

每一步都必须包含工程师需要的**实际内容**。以下是**计划失败**——绝不允许出现：

- "TBD"、"TODO"、"后续实现"、"填入细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "为上述内容编写测试"（不附实际测试代码）
- "类似 Task N"（重复写出代码——执行者可能不按顺序阅读任务）
- 只描述做什么但不展示怎么做的步骤（代码步骤必须有代码块）
- 引用未在任何任务中定义的类型、函数或方法

## 铁律

- 始终给出精确文件路径
- 每一步都包含完整代码——如果一步涉及代码变更，展示代码
- 给出精确命令和预期输出
- DRY、YAGNI、TDD、频繁提交

## 与 TDD 协同

计划中的每个实现任务必须显式遵循 Red → Green → Refactor 循环：

- Step A: 编写失败测试（Red）
- Step B: 运行确认失败
- Step C: 最小实现使测试通过（Green）
- Step D: 运行确认通过
- Step E: 重构（Refactor）——仅在测试全绿时
- Step F: 提交

## 计划自审

编写完整计划后，用全新眼光对照规格检查：

**1. 规格覆盖度：** 浏览规格中的每个章节/需求。能指向实现它的任务吗？列出差距。

**2. 占位符扫描：** 搜索计划中的红旗——任何"严禁占位符"一节中的模式。修复。

**3. 类型一致性：** 后面任务中使用的类型、方法签名、属性名是否与前面任务中定义的一致？Task 3 中叫 `clearLayers()` 但 Task 7 中叫 `clearFullLayers()` 就是 bug。

发现问题直接内联修复。如果发现规格需求没有对应任务，添加任务。

## 执行交接

计划保存后，提供执行方式选择：

> **"计划已保存到 `<path>`。两种执行选项：**
>
> **1. 子代理驱动（推荐）** — 每个任务分派一个全新子代理，任务间审查，快速迭代
>
> **2. 内联执行** — 在当前会话中逐任务执行，设检查点供人工审阅
>
> **选择哪种？"**
